# Working with Concepts

Use this when concepts or relationships are introduced, ambiguous, or changing. If the accepted model is sufficient, use it without adding new records.

1. Find the glossary for the relevant domain context through the project map or navigation. Clarify an ambiguous context; an identical name alone does not require a shared definition.
2. Immediately point out any conflict between the meaning under discussion and the glossary, and propose a precise term. If the request does not resolve the difference, record the question in the decision tree.
3. Devise a boundary scenario that distinguishes possible interpretations of the concept or relationship. Explicitly label it as a thought experiment: it does not by itself confirm an existing path or add a requirement.
4. Check claims about current behavior against code and documents, presenting material contradictions. Distinguish current behavior, accepted changes, and hypotheses.
5. Immediately after acceptance, update the canonical definition, usually in 1–2 sentences, and identify any target meaning not yet implemented. If confusion is likely, list undesirable synonyms; do not include rejected alternatives in the accepted model.
6. Keep domain definitions in the glossary; leave requirements, detailed behavior, and implementation in their respective documents. Do not add general programming concepts without domain-specific meaning; create a new glossary only when there is no suitable place for the accepted definition.
