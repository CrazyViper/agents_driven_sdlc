# agents_driven_sdlc

Девять скилов Codex для подготовки и реализации изменений в программном продукте. Общий CR связывает UX-макет, постановку, сценарии, требования, архитектуру, тесты и план работ. Правила конкретного проекта берутся из его `AGENTS.md` и документации.

**UX-дизайнер → верификация макета пользователем → продакт → аналитик и архитектор → тестировщик → планировщик → ревьюер решения → утверждение всего пакета → исполнение оркестратором.**

UX-этап нужен для нового или изменённого UI. При отсутствии UI оркестратор фиксирует причину пропуска и начинает с продакта. Медиация вызывается при разногласии во время подготовки решения или ревью кода; без спора отдельного этапа медиации нет.

## Скилы и результаты

| Роль и скил | Ответственность и результат |
| --- | --- |
| [Оркестратор](skills/orchestrator/SKILL.md) | Ведёт процесс, передаёт канонические схемы и правила, организует возвраты и медиацию. Предъявляет обзор изменения и граф плана; после утверждения ведёт реализацию. |
| [UX-дизайнер](skills/ux-designer/SKILL.md) | Готовит интерактивный макет к верификации. При сложной навигации добавляет карту переходов; передаёт решения, гипотезы и ограничения демонстрации. |
| [Продакт](skills/define-product-change/SKILL.md) | Через `grilling` и `domain-modeling` уточняет задачу. Ведёт CR и словарь, показывает границы изменения и доменную модель диаграммами с основаниями выбранного подхода. |
| [Аналитик](skills/develop-user-scenarios/SKILL.md) | Строит диаграммы сценариев и значимых состояний, связывает их с точными ФТ и НФТ. |
| [Архитектор](skills/design-project-architecture/SKILL.md) | Готовит схемы компонентов, взаимодействий, данных и классов, точные контракты и карту изменяемых файлов, включая тесты и окружение. |
| [Тестировщик](skills/design-test-scenarios/SKILL.md) | Показывает покрытие веток и состояний картой проверок. Задаёт точные условия, ожидаемые результаты, данные, подготовку и очистку окружения. |
| [Планировщик](skills/plan-change-implementation/SKILL.md) | Распределяет объём карты архитектора по графу проверяемых этапов с результатами и зависимостями. Дополняет его ссылками на изменения и условиями приёмки. |
| [Ревьюер решения](skills/review-solution/SKILL.md) | Проверяет полноту, актуальность и целостность пакета, смысл и читаемость схем, точность правил и пользу пояснений. Возвращает замечания и вердикт. |
| [Медиатор](skills/mediate-solution/SKILL.md) | Нейтрально исследует основания разногласия и ведёт лог. В сложном споре показывает развилку диаграммой, сохраняя решающие факты и изменения позиций в пояснениях. |

## Формат артефактов

[Общие правила диаграмм](skills/orchestrator/references/diagrams.md) действуют и в полном пайплайне, и при самостоятельном вызове предметного скила. Связи, потоки, состояния и зависимости составляют содержание схем. Под каждой схемой остаются дополняющие основания, ограничения, допущения и источники. Перечни нарисованных объектов и пересказ стрелок удаляются. Определения, точные требования, контракты, команды и ожидаемые результаты проверок сохраняются текстом или таблицами.

Формат по умолчанию: Mermaid `.mmd`, сгенерированный `.svg` рядом и превью с пояснениями в принятом Markdown-документе. Внутри документов используются относительные ссылки. Авторы обновляют источник, экспорт и пояснения вместе, проверяют смысл, ссылки и отрендеренное изображение. Ревьюер оценивает это в рамках обычного ревью пакета.

Состав схем определяется вопросами изменения. Полный каталог понятий или всех полей БД нужен только по запросу или правилам проекта. У каждого решения один владелец; следующие роли ссылаются на его материалы и создают другое представление только для другого вопроса. Источники схем и точные правила передаются исполнителям вместе с превью.

## Подготовка решения

UX-дизайнер получает идею и источники, собирает изолированный интерактивный макет и проверяет его существенные состояния. Создание макета и локальный preview входят в подготовку до разрешения реализации. Оркестратор показывает макет в основном чате, получает реальный ответ пользователя и возвращает правки тому же дизайнеру. Только координатор фиксирует `VERIFIED` для показанной версии. Уже проверенную применимую версию повторно согласовывать не нужно. Отдельный UX-ревьюер подключается по запросу или существенной сложности; его вывод не заменяет верификацию пользователем.

Продакт получает идею, проверенный макет и доступный контекст проекта, уточняет существенные неизвестные и фиксирует продуктовые решения. Он использует `grilling` и `domain-modeling` из пакета `mattpocock-skills`. Дизайнер передаёт гипотезы, демонстрационные допущения и ограничения явно; они не становятся требованиями и каноническими понятиями автоматически. Уже полученные ответы и подтверждённые сведения используются повторно. Простые факты продакт выясняет напрямую; самостоятельное исследование делегирует, когда от этого есть польза.

Аналитик готовит сценарии и требования, затем архитектор использует их для детального проектирования. Обоим доступен актуальный макет с принятыми решениями. При необходимости они уточняют зависимые материалы друг у друга. Новые понятия, доменные объекты и изменения поведения возвращаются продакту: аналитик, архитектор и UX-дизайнер не вводят их в каноническую модель самостоятельно. Содержательные изменения проверенного UI возвращаются дизайнеру и проходят верификацию затронутой части пользователем.

Тестировщик определяет сценарии, ожидаемые результаты и необходимые условия проверки: значимые данные и вариации, изоляцию, подготовку и очистку окружения. Общие условия записываются один раз или связываются с действующими процедурами проекта; в сценариях остаются отличия. Подробности нужны для воспроизводимости и оценки результата. Правила тестирования проекта имеют приоритет над общими инструкциями скила. По явному запросу пользователя тестировщик может предложить конкретное содержание данных.

До планирования архитектор учитывает результат тестировщика в карте изменяемых файлов. Планировщик распределяет эту карту по этапам с учётом зависимостей. Он не назначает новые файлы и не проводит проверку архитектуры или актуальности решения. Если покрытие этапа недостаточно, планировщик возвращает аргументированный вопрос тестировщику; дополнительные тесты появляются только для существенного пробела.

Ревьюер получает весь пакет после подготовки плана, включая актуальный макет и подтверждение его верификации либо основание отсутствия UI. Он может вернуть конкретную часть её владельцу на любом предыдущем этапе или сформулировать вопросы пользователю. Согласованное исправление возвращается тому же ревьюеру. При изменении одной части обновляются затронутые связи, а не весь пакет без причины.

Артефакты размещаются по правилам проекта и связываются из CR. Деталь нужна, если без неё неоднозначны выбор, поведение, контракт, риск, проверка или работа следующей роли. Ход исследования, пустые разделы и подробности реализации без влияния на контракт опускаются. Явно запрошенные подробности и обязательные сведения проекта сохраняются.

Уточняющие вопросы задаются по мере необходимости: все вопросы текущего раунда, чьи предпосылки уже известны, явно предъявляются общим пакетом в тексте одного ответа вместе с вариантами, последствиями и обоснованными рекомендациями. Пользователь может взять время на обдумывание и выбор ответов; зависимые решения ждут его ответа. Отдельного утверждения постановки, требований, архитектуры или плана между этапами нет.

## Медиация

Автор решения или исполнитель кода вправе аргументированно не согласиться с замечанием ревьюера. Разногласие между предметными авторами тоже может потребовать медиации. Ревьюер проверяет чужую работу, но в споре о собственном замечании остаётся одной из сторон.

Оркестратор вызывает отдельного медиатора, передаёт предмет спора, участников, версии материалов и аргументы, затем ждёт результата. Медиатор объясняет всем один [протокол медиации](skills/mediate-solution/references/discussion.md). Этот документ содержит общие правила дискуссии. Управление обсуждением и ведение лога описаны только в [скиле медиатора](skills/mediate-solution/SKILL.md).

Медиатор задаёт прорезающие вопросы, проверяет факты и применимость оснований, ведёт цепочку «почему так» и ищет наиболее вероятное расхождение. Он предлагает минимальное решение, сохраняя подтверждённые обязательства. Если нужна дополнительная компетенция, медиатор явно запрашивает консилиум; оркестратор собирает нужных участников, а дискуссия и лог остаются у медиатора.

Изменения выполняют владельцы материалов. При споре на ревью исправления проверяет соответствующий ревьюер. Ранний спор авторов закрывается подтверждением владельцев затронутых частей без ожидания будущего общего ревью. Если для разрешения спора нужен недоступный факт или выбор пользователя, медиатор возвращает адресный вопрос и указывает зависимую работу.

Каждый спор документируется по ходу обсуждения. Лог содержит существенные позиции и их изменения, решающие основания и источники, найденное расхождение, решение и подтверждённые действия. Вопросы и ответы сохраняются, когда они меняют решение или фиксируют открытый блокер; стенограмма не нужна. Снятые замечания и основания их снятия сохраняются. Закрытие спора не заменяет вердикт ревьюера. Открытый спор блокирует связанную с ним приёмку.

## Утверждение пользователем

После `ACCEPT` ревьюера решения оркестратор останавливается и предъявляет проверенную версию пакета:

- обзорную схему изменения и граф этапов из материалов авторов, дополняя их основаниями, компромиссами, ограничениями и результатом UX-верификации и ревью;
- ссылки на CR, актуальный макет при наличии, план и вердикт ревью; остальные предметные материалы доступны из CR;
- краткие итоги каждой медиации со ссылками на все логи, включая снятые замечания.

Пользователь одним решением утверждает весь пакет вместе с планом и разрешает реализацию. Верификация макета, ответы на уточнения и `ACCEPT` ревьюера сами по себе не разрешают менять рабочий код. При продолжении работы с той же утверждённой версией повторное утверждение и новое составление плана не нужны.

## Реализация

Оркестратор применяет [инструкции исполнения](skills/orchestrator/references/execution.md) и выполняет этапы последовательно:

1. Для этапа запускает нового исполнителя `worker`, передаёт относящиеся к этапу разделы пакета, область файлов, ожидаемый результат, проверки и правила данных. Ссылки на полные документы остаются доступными.
2. Исполнитель меняет код, тесты и документацию, подготавливает среду и данные, выполняет проверки и очистку. В отчёте фиксирует команды, исходы, проверенную версию и условия, состояние среды и отклонения.
3. Отдельный ревьюер проверяет исходники и diff, соответствие утверждённому этапу, тесты и политику данных. Исправления выполняет тот же исполнитель, а перепроверку ведёт тот же ревьюер. Аргументированный спор передаётся медиатору.
4. После `ACCEPT` и закрытия споров оркестратор проверяет diff и применимость результатов проверок к текущей версии. Подтверждённые результаты можно использовать повторно. Повтор нужен при изменении проверяемого кода, среды или данных, недостоверном результате, существенном непроверенном риске либо явном требовании независимого прогона. Следующий этап начинается после приёмки текущего.
5. После всех этапов новый отдельный ревьюер проверяет полный diff по всему утверждённому пакету. Оркестратор обеспечивает результаты итогового набора проверок и предусмотренную визуальную проверку, если она требуется.

Обязательная проверка без результата или с ошибкой не считается пройденной. Новые проверки сверх согласованного покрытия требуют конкретного основания. После завершения пользователь получает выполненные этапы, вердикты, фактические проверки, состояние среды после очистки, ограничения и сводки всех медиаций реализации со ссылками на логи.

Исправления дефектов внутри утверждённых границ проходят обычное ревью кода. Содержательное изменение поведения, доменной модели, архитектуры или объёма возвращается владельцам решения; обновлённый пакет проходит ревью и утверждение пользователем.

Утверждение пакета разрешает локальную реализацию. Доступ к production требует явного разрешения, включая чтение. Для остальных внешних источников учитываются область запроса и уже выданные разрешения. Commit, push, PR и release выполняются по прямому разрешению в плане или отдельному явному запросу пользователя.

## Участники и настройки

Предметные роли, ревьюеры и медиатор работают в отдельных субагентах `default`; исполнители реализации используют `worker`. Оркестратор передаёт точный скил, контекст и область ответственности. Каждый участник учитывает чужие изменения в общей рабочей директории. Постоянные TOML-конфигурации ролей не требуются; UI-метаданные каждого скила находятся в его `agents/openai.yaml`.

| Участники | Настройки по умолчанию |
| --- | --- |
| UX-дизайнер, UX-ревьюер при необходимости, остальные авторы пакета и ревьюер решения | `gpt-6-astra`, `xhigh` |
| Исполнители и ревьюеры реализации | `gpt-5.6-sol`, `xhigh` |
| Медиатор | Модель сторон и уровень на одну поддерживаемую ступень выше максимального уровня сторон; для `xhigh` это `max` |

Настройки запуска проверяет оркестратор. Если требуемая модель или повышение уровня недоступны, он сообщает ограничение и запрашивает допустимые параметры. Молчаливой замены модели или понижения сторон нет. Явные настройки пользователя имеют приоритет.

Имена субагентов содержат роль, этап или CR и характерное имя деятеля науки: `architect_cr07_turing`, `tester_cr07_fisher`, `worker_step02_hopper`, `mediator_step02_noether`. Имя помогает различать участников и не задаёт им взгляды или манеру рассуждения.

## Использование

Для полного цикла передай оркестратору идею, контекст проекта и известные ограничения:

```text
Используй $orchestrator, чтобы подготовить полный пакет решения по этой идее,
показать его мне на утверждение и затем исполнить согласованный план: …
```

Для продолжения укажи CR, утверждённую версию и текущее состояние плана. Для отдельной предметной задачи используй соответствующий скил напрямую. Например, аналитик может описать существующее поведение без создания нового CR; реальные продуктовые и доменные неопределённости передаются продакту.

Для подготовки одного интерфейса:

```text
Используй $ux-designer, чтобы по этим материалам собрать кликабельный макет
нового интерфейса и показать его мне на верификацию: …
```

## Установка

В Codex должны быть доступны зависимости продакта `grilling` и `domain-modeling` из `mattpocock-skills`. Установщик этого репозитория их не устанавливает.

```bash
./scripts/install.sh
```

Скрипт создаёт симлинки девяти скилов из `skills/` в `~/.agents/skills` и обновляет одноимённые ссылки при повторном запуске. Обычные файлы и каталоги с совпадающими именами не перезаписываются. Скилы не копируются в проекты.

Для другого пользовательского каталога:

```bash
AGENTS_SKILLS_DIR=/path/to/skills ./scripts/install.sh
```

Если Codex не показывает изменения автоматически, перезапусти приложение.
